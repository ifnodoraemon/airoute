# 并发扣费修复记录（2026-11-06）

范围：当前工作区的钱包、Key 预算、请求预授权、批量结算、异步任务和 Key 分组选择。测试使用临时数据库及独立容器，没有向运行中的业务库写入测试数据或调用生产付费上游。

## 已完成的修复

| 原问题 | 当前行为 | 主要实现 |
| --- | --- | --- |
| 预估补差不足仍调上游 | 整笔预估金额必须获得预留，否则在调度前返回 402 | `api/quota_admission.go`、`middleware/request_quota.go` |
| 按实际成本释放汇总额，误删其他请求预留 | 以请求 ID 精确释放，重复释放不能影响其他请求 | `storage/billing_reservation_settlement.go` |
| 等待超时归还额度，数据库余额尚未扣款 | 预留一直保留，扣款和释放在同一事务提交 | `storage/settlement_commit.go` |
| 余额读取和预留跨数据库 / Redis，存在旧快照窗口 | 余额、Key 已用量和待扣预留在同一数据库事务锁内检查 | `storage/billing_reservation_gate.go` |
| Redis 故障退为各副本独立金额限制 | 金额权限不再依赖 Redis；数据库不可用则拒绝付费准入 | `middleware/request_quota.go` |
| Key budget 只检查已结算消费 | Key 预算同时包含在途及待结算金额 | `storage/billing_reservation_gate.go` |
| 钱包负值被钳制，实际消费被自动免掉 | 完整记录实际费用及欠款，拒绝后续无资金覆盖的请求 | `storage/wallet_deduct.go`、`storage/settlement_postgres.go` |
| 队列丢失或扣款后审计失败可能丢失证据 | 待结算日志保存在数据库，审计提交后才删除，可独立恢复 | `storage/billing_usage_journal.go` |

预留由迁移 54 创建的 `billing_reservations` 保存，待结算证据保存在 `billing_usage_journal`。旧的进程内和 Redis 金额计数器、TTL heartbeat、按实际费用释放接口已经删除。

## 入口与生命周期

- 普通聊天、流式聊天、Responses、Anthropic、Gemini、MCP 均在调度前检查完整补差结果。没有显式输出上限的付费调用，在实际请求中加上 4096 token 上限；已提供的协议上限保留。估算还覆盖多候选输出、缓存写入溢价、映射模型费率及固定费用。
- Embeddings、Rerank、图片、音频、视频和 Moderation 的金额估算也进入同一预留检查。
- 内联 Gemini 批任务逐项估算并写入输出上限。异步任务的原始付款身份和预留 ID 随原生状态保存，终态结算释放原预留；失败且未报告消费的交互会归还预留。
- Live 会话在实际 setup 中限制输出，并在转发新输入、观察用量增长时补足预留；不足则结束会话，已消费金额仍入账。
- 读取已付费结果及取消已有任务不要求再次付费预留，但仍检查身份、账户状态和资源归属。
- 新建 Key 改为已有分组下拉框；分组目录来自定价管理。创建和显式调整 Key 分组的后端接口也拒绝未知名称。

Gemini Interactions 的模型输出上限使用官方的 `generation_config.max_output_tokens` 字段；该配置适用于模型调用。[Google 接口文档](https://ai.google.dev/api/interactions-api)

## 验证

- 余额 1 元、默认 0.05 元初始预留的 50 个并发请求，只能取得 20 个预留。补到无法覆盖的金额会整笔拒绝，不会部分补差后继续。
- A、B 各自预留后，A 超出估算、完成结算或重复释放，B 的预留保持原值。
- 人为延迟批量提交并缩短调用等待，后续请求不能再次使用待扣余额；提交后也不能利用旧余额快照重新取得预留。
- PostgreSQL 16 的两个独立连接池同时发起 64 个申请：余额 1 元、每单 0.05 元，恰好放行 20 单。并发结算和重复投递后总扣款为 1 元、余额为 0、预留为 0。
- 待结算日志可在没有 Redis / 内存队列的情况下恢复扣款与审计；审计写失败后日志仍存在，恢复不会重复扣款。
- 已执行六类变异：关闭金额校验、按 Key 误删所有预留、允许取消待扣预留、漏写真实请求输出上限、扣款后提前删除恢复日志、重新启用透支钳制。对应回归均失败，源码通过 overlay 保持字节一致。
- 数据库不可用时，钱包用户、无用户归属但设置预算的 Key、设置预算的管理员 Key 都拒绝付费调用；额外的 fail-open 变异也被回归捕获。
- 分组校验的前后端变异测试能捕获绕过；Node.js 22.23.4 下前端全量 807 个测试、零告警 lint 和生产构建已通过。

- Go 1.26.1 下 `go test -race -count=1 ./...` 全量通过；显式配置独立测试数据库和 Redis 后，PostgreSQL / Redis / 用量分区相关集成测试也全部通过。

以上正确性验证不等于对生产集群安全 QPS 的承诺。

## 上线与运行边界

1. 先排空旧版付费在途请求、待结算记录及提供商任务，再统一切换所有副本；不能混用旧 Redis 预留和新数据库预留。
2. 预留及待结算日志是资金状态，不能按缓存清空。没有可恢复用量证据的异常中断会保留预留，需与提供商核实后处理，不能静默超时归还。
3. 文件输入的原生批任务无法事先计算完整金额，付费调用返回 422，需改为内联输入。付费原生 Agent 调用需使用纯固定费用，变量 token 费用无法覆盖其内部工作上限。
4. 预授权基于估算和当时可知的费率。提供商实际计数异常、估算偏差或执行期间调价造成超额时，费用完整记为欠款，并阻止后续无资金覆盖的请求；不再通过钳制余额免掉差额。
