## 1. 决策

2026-10-28 产品决策：**收窄 v1.1 范围，删除四项能力**。

删掉的四块能力：

1. **组织与成本中心**（组织树、成员、归属、组织维度看板/出账）
2. **预算与告警**（多级预算、阈值事件、通知中心）
3. **钱包资金流水**（管理员侧资金流水账本、查询与导出）
4. **成本与毛利**（供应商成本核算、毛利/毛利率、成本分析、用量日汇总）

**唯一保留的 v1.1 新增治理能力：供应商模型单价维护**，并放进**定价页与我们的售价并排展示**。既有的个人用量 / 密钥配额水位视图不属于被删的四项能力，保持现状（只展示既有 key 级配额与速率限制，不新增组织/预算维度）。

口径约束：

- **我们的售价 ≠ 供应商价**：售价（目录价 × 分组倍率、缓存/分时价目）与供应商单价（按「渠道名 + 模型」记录）是两套独立数据，**分开维护**，不互相推算。
- 供应商单价只用于**比价与议价**参考：不参与扣款、不写审计行的成本字段、**不计算毛利/毛利率/成本覆盖率**，也不做成本分析报表。
- 定价页并排展示：按模型把我们的售价与供应商单价并排显示（含两者价差）；供应商价未配置时显示为“未配置”，**不按 0 处理**（避免把缺失当免费）。

决策理由（简述）：四项能力的运营与口径成本高（组织归属回填、跨副本预算计数一致性、资金流水账本对账、成本覆盖率口径），与当前“单团队、单个管理员、一套钱包”的使用形态不匹配；而「供应商单价与售价并排」已能满足比价与成本议价诉求，且不引入新的数据面依赖与账本风险。详见 [ROADMAP](../ROADMAP.md) 的现状基线与判断。

## 2. 删除清单

### 2.1 管理 API 端点

以下端点随能力一起删除（不再注册路由，文档与前端同步移除）：

| 端点 | 能力 |
|---|---|
| `GET/POST /api/v1/admin/orgs`、`GET/PUT/DELETE /api/v1/admin/orgs/:id` | 组织 CRUD |
| `POST /api/v1/admin/orgs/:id/move` | 组织移动 |
| `GET/POST /api/v1/admin/orgs/:id/members`、`DELETE /api/v1/admin/orgs/:id/members/:user_id` | 组织成员 |
| `GET/POST/PUT/DELETE /api/v1/admin/budgets` | 预算规则 |
| `GET /api/v1/admin/budgets/:id/events` | 预算阈值事件 |
| `GET /api/v1/admin/wallet/transactions`、`GET /api/v1/admin/wallet/transactions/export` | 管理员侧资金流水与导出 |
| `GET /api/v1/user/wallet/transactions` | 用户侧资金流水查询（同一账本） |
| `GET /api/v1/admin/cost/overview`、`/cost/breakdown`、`/cost/trend` | 成本总览 / 分组 / 按日趋势 |

> 边界说明：删除的是**资金流水账本**能力（`wallet_transactions` 及其管理员侧/用户侧查询与导出）。**钱包余额**、**充值**（Stripe / 沙箱）、**兑换码**、**充值订单查询**属于既有能力，不在本次删除清单内；供应商价目与售价价目端点保留（见第 3 节）。

### 2.2 控制台页面

| 页面 / 组件 | 处理 |
|---|---|
| 组织树与成员管理（`OrganizationsView`） | 删除页面与导航入口 |
| 预算与告警 / 告警中心（`BudgetsView`） | 删除页面与导航入口 |
| 资金流水页（账本查询/导出） | 删除页面与导航入口 |
| 成本分析页（毛利、分组、按日趋势）（`CostAnalyticsView`） | 删除页面与导航入口 |
| 定价页（`PricingManager`） | **保留并收敛**：只保留售价维护 + 供应商单价维护 + 并排视图（`SupplierCostPanel`）；删除成本/毛利相关列、图表与入口 |
| 自助仪表盘（`MyUsageView`） | 保留既有能力：个人用量、密钥配额与速率限制水位 |

### 2.3 数据面行为

| 行为 | 处理 |
|---|---|
| **预算闸门**：认证后预算预检、超限 `402 budget_exceeded` / `X-Airoute-Budget-Warning`、预算计数（内存 + Redis `INCRBY`）、30s 回写、6h 对账 | 删除；请求准入回到“key 状态 → 钱包余额 → 在途额度”的既有链路 |
| **组织归属**：认证上下文 `org_id`、审计行/结算行写 `org_id`、新用户/新 key 继承属主组织 | 删除；`org_id` 不再注入、不再写入 |
| **`cost_basis` 记录**：响应后按 渠道 + 模型 解析供应商价目并写 `usage_logs.cost_basis_units`、成本引擎与缓存 | 删除；不再计算与写入（`cost_basis_units` 列由 v40 删除，见第 4 节） |
| **用量日汇总**：`usage_daily` 后台按小时增量聚合、日切重算、成本趋势按需重建 | 删除；不再有日汇总 worker 与重建路径 |

| 对象 | 处理 |
|---|---|

## 3. 保留清单

### 3.1 供应商模型单价（唯一保留的 v1.1 治理增量能力）

| 层面 | 内容 |
|---|---|
| 数据 | `supplier_costs` 表：以「渠道名 + 模型」为唯一键（`UNIQUE(channel, model)`），记录输入/输出**每百万 token 的供应单价**（以 1e-9 CNY 为整数单位存储）与启用状态（`active` / `disabled`） |
| 管理 API | `GET /api/v1/admin/supplier-costs`（列表）、`POST /api/v1/admin/supplier-costs`（按渠道 + 模型新增/覆盖）、`DELETE /api/v1/admin/supplier-costs/:id`（删除）、`GET /api/v1/admin/supplier-costs/export`（CSV 导出）、`POST /api/v1/admin/supplier-costs/import`（CSV 导入） |
| CSV 导入导出 | 列为 `channel,model,input_cost,output_cost,status`，导出带表头可回填；导入识别表头、单次上限 5000 行、逐行报错、`dry_run=1` 只校验不写入，全部校验通过后按行 upsert；校验失败整批不写入。口径与实现沿用裁剪前已完成版本，本次不改变 |
| 定价页并排视图 | 定价页「供应商单价」子视图：以**模型**为轴，把我们对该模型的售价（默认分组价）与供应商单价并排展示，并标出价差（我们的售价 − 供应商价）；两套价目独立维护、互不推导；未配置的供应商价显示“未配置” |

### 3.2 明确不做（保留能力内也不做）

- 不基于供应商价计算毛利、毛利率、成本覆盖率，也不做成本分析报表（定价页的价差只是两套价目的差值展示，不落库、不进报表）；
- 不把供应商价写入 `usage_logs`（不落 `cost_basis`）；
- 不参与扣款、结算、账单与预算判断；
- 不做按组织/部门/项目的归属、出账与配额继承。

## 4. 数据库对象

四项能力在数据库侧**彻底移除**，不保留遗留对象：迁移 **v40 `drop_legacy_governance_objects`** 在升级时直接删除旧库中的相关表、列与索引。全新数据库本就不创建这些对象。

| 类型 | 对象 | 处理 |
|---|---|---|
| 表 | `budget_events`、`budgets`、`wallet_transactions`、`org_memberships`、`orgs`、`usage_daily` | v40 `DROP TABLE IF EXISTS`（子表 `org_memberships` 先于父表 `orgs`） |
| 列 | `users.org_id`、`api_keys.org_id`、`usage_logs.org_id`、`usage_logs.cost_basis_units`、`usage_logs.channel_id`、`billing_settlements.org_id` | v40 `ALTER TABLE … DROP COLUMN`（表/列不存在则跳过） |
| 索引 | `idx_usage_org_created`、`idx_usage_logs_channel_id`、`idx_users_org`、`idx_api_keys_org`、`idx_billing_settlements_org` | v40 先 `DROP INDEX IF EXISTS`，再删对应列 |
| 保留 | `supplier_costs`（含唯一约束 `UNIQUE(channel, model)` 与索引） | 继续使用；新库照常创建 |

要点：

- **新库更轻**：对应的建表/加列迁移随能力一起删除，全新安装不会创建这些表和列，也无需清理步骤。
- **v40 幂等可重放**：全部使用 `IF EXISTS` 并对表做存在性检查，DDL 与版本记录之间崩溃后重放安全。
- **不写 down migration**：删除是单向的，仓库不提供恢复这些对象的迁移或脚本。

## 5. 升级与回滚影响

### 5.1 升级（不可逆）

- **升级即删除**：旧库首次以本版本启动时会执行 v40，**直接 DROP** 上述 6 张表、6 个列与 5 个索引。历史组织归属、预算与告警事件、钱包资金流水、用量日汇总与成本数据**不会保留**。
- **不可恢复**：删除后无法从数据库内找回；需要保留这些历史数据（对账、取证、迁移到其他系统）的，**必须在升级前备份数据库**。
- **新库无需清理**：全新安装本就不创建这些对象，v40 对其为空操作。
- **滚动升级**：v40 会在第一个新版副本启动时执行；仍在运行的旧副本若访问被删对象会报错，建议在停机窗口升级或尽快完成全量替换。
- **配置侧**：`GATEWAY_ALERT_*` 已不再读取；旧 `.env` 中残留也不会生效，进程内不再发送预算告警（集群监控仍由 Prometheus 规则负责）。

### 5.2 回滚

| 场景 | 影响 |
|---|---|
| 回退到裁剪前的二进制 | 表与列已被 v40 删除、不会重建，旧版本读取这些对象的路径（组织、预算、钱包流水、成本分析）会失败；其余功能可运行 |
| 需要恢复裁剪前的数据 | 只能从**升级前备份**恢复；升级后再回滚二进制也拿不回已删除的历史数据 |
| 数据库结构降级 | 不做。没有 down migration，回滚只回退二进制 |
